# BE Harness — 백엔드 작업 오케스트레이터

WebVideoChat 백엔드 작업을 전문 에이전트 팀으로 조율한다. **실행 모드: 에이전트 팀.**

## 제1원칙 — 점진적이고 되돌릴 수 있게

이 프로젝트는 원래 단일 프로젝트였고, MSA 전환을 위해 **지금은 FE/BE만 강제 분리한 과도기**다. 소스는 불완전할 수 있다. 따라서:

- **한 번에 크게 바꾸지 않는다.** 모든 작업을 "독립적으로 검증·롤백 가능한 최소 스텝"으로 쪼갠다. 오류 발생 시 되돌리기 쉽게 한다.
- **지금 당장 MSA로 쪼개지 않는다.** 최종 방향일 뿐, 현재 우선순위는 FE/BE 분리 상태의 안정화와 결합도의 점진적 감소다.
- **소스가 깨져 있을 수 있음을 전제한다.** "내가 깬 것"과 "원래 깨져 있던 것"을 항상 구분해 보고한다.

## 팀 구성

| 에이전트 | 역할 | 타입 |
|---------|------|------|
| `be-architect` | 점진적 리팩토링 계획, 결합도 분석, 다음 한 스텝 설계 | general-purpose |
| `be-engineer` | Spring Boot 코드 구현·수정 | general-purpose |
| `contract-qa` | FE↔BE 경계면 정합성 검증 | general-purpose |
| `devops` | GitHub Actions·Docker·nginx·배포 | general-purpose |

모든 Agent 호출은 `model: "opus"`로 한다. 각 에이전트 정의는 `.claude/agents/`에 있다.

## Phase 0: 컨텍스트 확인

작업 시작 전 실행 모드를 판별한다:
- `_workspace/` 존재 + 부분 수정 요청 → **부분 재실행**(해당 에이전트만 재호출)
- `_workspace/` 존재 + 새 작업 → 기존 `_workspace/`를 `_workspace_prev/`로 이동 후 **새 실행**
- `_workspace/` 미존재 → **초기 실행**(`_workspace/` 생성)

## Phase 1: 작업 분류 및 라우팅

요청을 유형별로 분류해 필요한 에이전트만 투입한다(과잉 투입 금지):

| 작업 유형 | 투입 에이전트 | 흐름 |
|----------|-------------|------|
| 구조 개선/리팩토링 | architect → engineer → contract-qa | 설계 → 구현 → 검증 |
| 기능/버그 수정 | engineer → contract-qa | 구현 → 검증 (계약 영향 시) |
| 계약/정합성 점검 | contract-qa 단독 | 검증만 |
| 배포/CI 변경 | devops (→ contract-qa: 환경변수 매핑) | 파이프라인 수정 |
| 배포 환경 증상 디버깅 | engineer/devops | 원인 추적 → **보고 시 `cicd-management/references/deploy-symptom-triage.md`를 로드해 증상 분류별 "레포 밖 점검 항목"(nginx WS 프록시·CORS·프로파일·env·동시성 등) 체크리스트를 자동 생성**해 사용자에게 제시 |
| PR 생성/리뷰/병합 | `pr-merge-flow`(pr-reviewer·engineer) | PR 생성 → opus 적대적 검수 → blocker 수정(최대 2R) → 조건부 자동병합(blocker 0+CI green). 단일 BE 레포 PR일 때. 직접 `pr-merge-flow` 스킬로도 트리거됨 |
| 복합 작업 | architect가 스텝 분할 후 분배 | 스텝별 순차 |

> **배포 증상 디버깅 규칙:** "배포했는데 X가 안 된다"류는 레포 코드만 보면 레포 밖 원인(프록시·CORS·프로파일·캐시·동시성)을 놓치기 쉽다. 반드시 `deploy-symptom-triage.md`로 증상 분류 후 레포 밖 점검 항목을 체크리스트화해 보고한다. 교차 레포 증상이면 관제탑(webvideochat-control)으로 올린다.

## Phase 2: 팀 실행

1. `TeamCreate`로 필요한 멤버만 팀 구성.
2. `TaskCreate`로 의존 관계를 명시한 작업 생성(설계 → 구현 → 검증 순서 의존).
3. 팀원은 `SendMessage`로 직접 조율하고, 산출물은 `_workspace/{phase}_{agent}_{artifact}.md` 파일로 공유.
4. **각 스텝 완료마다 빌드 확인**(`./gradlew build`)과 점진 계약 검증을 거친 뒤 다음 스텝으로 진행.
5. 리더(오케스트레이터)는 진행을 모니터링하고 결과를 종합한다.

### 데이터 전달
- **태스크 기반**(조율) + **파일 기반**(산출물, `_workspace/`) + **메시지 기반**(실시간).
- 중간 산출물(`_workspace/`)은 보존(감사·롤백 추적용), 최종 결과만 코드에 반영.

## Phase 3: 종합 및 보고

- 변경 요약, 빌드/검증 결과, 발견된 경계 불일치(등급별), 롤백 방법을 사용자에게 보고.
- **계약에 영향을 준 변경이 있으면**, 이는 단일 레포로 끝나지 않는다 → 상위 **관제탑**(`WebVideoChat/.claude/`)으로 에스컬레이션한다: `contract-steward`가 계약 정본(`contract-spec.canonical.md`)을 갱신하고 FE 거울까지 동기화하며, `release-coordinator`가 FE 동반 변경과 배포 순서를 조율한다. 관제탑이 없으면(레포 단독 실행) 최소한 "FE 측 동일 변경 + 양쪽 contract-spec 동기화 필요"를 명시 보고한다.

## 에러 핸들링

- **빌드 실패**: 내 변경 때문이면 engineer가 1회 수정 시도, 재실패 시 롤백 후 보고. 원래 깨진 것이면 위치만 보고하고 진행 여부를 사용자에게 확인.
- **계약 BLOCKER 발견**: 해당 변경을 중단하고 수정 후 재검증. 양쪽(FE/BE) 동시 수정 필요 시 사용자에게 조율 보고.
- **상충/불확실**: 임의 결정하지 말고 출처 병기해 보고.
- **배포 변경**: 외부로 나가는 변경은 사용자 확인 없이 실행하지 않는다.

## 테스트 시나리오

**정상 흐름:** "방 입장 응답에 참가자 수를 추가해줘"
→ Phase 0(초기 실행) → architect가 "RoomEnterResponse에 필드 추가" 한 스텝으로 설계(계약 영향: 있음) → engineer 구현 + `./gradlew build` → contract-qa가 FE `RoomEnterResponse` 인터페이스와 대조해 "FE도 필드 추가 필요(BLOCKER)" 보고 → 사용자에게 FE 동반 수정 안내.

**에러 흐름:** "Signaling을 별도 서비스로 분리해줘"
→ architect가 "지금 한 번에 분리 불가, 인메모리 공유 상태부터 추출하는 것이 안전한 첫 스텝"으로 응답 → 작은 첫 스텝만 계획·제시 → 사용자 승인 후 그 스텝만 진행.

## 후속 작업

이 스킬은 "다시 실행", "이어서", "보완", "그 부분만 다시" 같은 후속 요청도 처리한다. Phase 0에서 `_workspace/`를 확인해 부분 재실행 여부를 판단한다.

## 진화

작업 완료 후 사용자에게 개선점을 묻는다. 피드백은 유형에 따라 에이전트 정의/스킬/이 오케스트레이터에 반영하고, `CLAUDE.md` 변경 이력에 기록한다.
